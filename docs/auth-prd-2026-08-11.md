## 一、产品目标（一句话）

让 GridMind 从「dev 工具角色假身份」升级为**真实账号体系**：用户点击 UserBadge 即可登录/切换/退出，登录后携带 JWT 访问受保护数据，角色从 JWT `role` claim 解析，**完全复用既有 RBAC 与 owner 校验语义，且 dev 本地体验零破坏**。

## 二、用户故事（每条含验收标准）

### US-1 未登录用户访问受保护页面 → 跳登录 / 弹登录层；登录后回跳原页面
- **场景**：未登录（无有效 access_token）用户打开任意页面。
- **验收标准**：
  - AC1-1：未登录访问**生产模式**受保护路由 → 重定向到 `/login`（或全局登录弹层），并记录 `redirect` 目标。
  - AC1-2：登录成功后自动跳回原页面（`redirect` 参数），无 redirect 时回首页。
  - AC1-3：**dev 模式不拦截**（保持现状零改动，见 US-10）。
  - AC1-4：登录页在未登录时也可直接通过 URL 访问（幂等）。

### US-2 登录失败 → 明确错误提示（不暴露账号是否存在）；错误次数过多限流
- **场景**：密码错 / 账号不存在 / 账号被禁用或锁定。
- **验收标准**：
  - AC2-1：密码错与账号不存在统一返回 `401 {"detail":"用户名或密码错误"}`（**不泄漏账号是否存在**）。
  - AC2-2：被禁用账号（`disabled=1`）→ `403 {"detail":"账号已被禁用"}`（仅提示禁用，不解释原因）。
  - AC2-3：账号锁定（`locked_until` 未过期）→ `423 {"detail":"尝试次数过多，账号已锁定，请稍后再试"}`。
  - AC2-4：同一账号连续失败 ≥5 次 → 锁定 15 分钟；锁定期间即使密码正确也拒绝（返回 423）。
  - AC2-5：登录接口叠加 IP 维度限流（slowapi，如 10 次/分钟/IP），超限 → 429。
  - AC2-6：登录失败事件写入审计日志（见 US-7）。

### US-3 登录成功 → 返回 access_token + refresh_token；前端保存；后续请求自动带 Authorization
- **场景**：合法用户输入用户名+密码登录。
- **验收标准**：
  - AC3-1：`POST /auth/login` 成功返回 `{access_token, refresh_token, token_type:"bearer", expires_in, user:{id, username, display_name, role}}`。
  - AC3-2：access_token 为 JWT，含 `sub`/`user_id`（= users.id）、`role`（5 角色之一）、`name`（展示名）、`iss`、`iat`、`exp`；**不含 `thread_id` claim**（避免命中 owner 快速路径 403）。
  - AC3-3：前端保存 token（存储位置见 §十 待确认；默认方案：access_token 存内存 Pinia + refresh_token 存 localStorage），后续所有请求经 `getAuthHeaders()` 自动带 `Authorization: Bearer <access_token>`。
  - AC3-4：登录成功后 UserBadge 立即刷新为「展示名 + 角色徽标」。
  - AC3-5：`GET /auth/me` 可用新 token 返回当前用户信息（前端据此校验会话有效性）。

### US-4 UserBadge 点击 → 下拉：当前用户/角色/退出/切换账号；退出清 token 跳登录
- **场景**：已登录用户点击 Header 右侧 UserBadge。
- **验收标准**：
  - AC4-1：点击 UserBadge 弹出下拉：顶部「展示名 + 角色徽标」，分隔线后「切换账号」「退出登录」；管理员额外显示「用户管理」入口（US-6）。
  - AC4-2：「切换账号」→ 清 token → 跳登录页（带 redirect 回当前页）。
  - AC4-3：「退出登录」→ 调 `POST /auth/logout`（revoke refresh_token）→ 清本地 token → 跳登录页。
  - AC4-4：dev 模式下拉额外显示「以 X 角色登录」快速切换（仅 dev，见 §九）。
  - AC4-5：下拉支持点击外部/Esc 关闭；无事件冒泡误触。

### US-5 Token 过期 → 自动用 refresh_token 续期；refresh 也过期则跳登录
- **场景**：access_token 过期（exp 到达）后继续操作。
- **验收标准**：
  - AC5-1：任一 API 返回 401（`Token expired`）→ 前端拦截器自动调 `POST /auth/refresh` 用 refresh_token 换新 access_token（**轮换** refresh_token，旧 refresh 作废），重放原请求。
  - AC5-2：刷新成功对用户**无感**（不弹窗、不丢输入）。
  - AC5-3：refresh_token 也失效/过期/被撤销 → 清 token → 跳登录页（带 redirect）。
  - AC5-4：并发多个 401 只触发**一次** refresh（Promise 去重），其余等待同一结果。

### US-6 管理员可在登录后访问用户管理页：创建/禁用用户、分配角色
- **场景**：admin 角色登录后管理用户。
- **验收标准**：
  - AC6-1：仅 `admin` 角色（生产）可访问用户管理页；非 admin 访问 → 403（页面隐藏 + 后端 `require_role(Role.ADMIN)` 兜底）。
  - AC6-2：可创建用户（用户名/邮箱/初始密码/角色），创建后默认 `must_change_password=1`。
  - AC6-3：可禁用/启用用户（`disabled` 翻转）；禁用后该用户所有 token 即刻失效（登录与 refresh 均拒绝）。
  - AC6-4：可修改用户角色（仅 5 角色之一）；角色变更在**下一个 access_token** 生效（现有 token 保留到过期，属可接受）。
  - AC6-5：管理员**不能**给自己降级为唯一非 admin 角色导致系统无管理员（防呆校验，可 P1 简化：允许但告警）。

### US-7 审计：登录/登出/失败/锁定/刷新事件写入审计日志
- **场景**：安全合规需要可追溯的认证事件。
- **验收标准**：
  - AC7-1：新建 `auth_audit_log` 表（与 `hitl_audit_log` 共存，独立表）。
  - AC7-2：记录事件：`login_success` / `login_failed` / `account_locked` / `logout` / `refresh` / `user_created` / `user_disabled` / `role_changed` / `password_changed`。
  - AC7-3：字段含 user_id、username、ip_address、user_agent、detail、created_at（UTC ISO）。
  - AC7-4：审计写库失败**不阻断**登录主流程（降级 loguru warning，勿把审计当硬依赖）。
  - AC7-5：审计读接口沿用 `verify_jwt_if_prod`（生产强制 JWT）；全量读按 `require_role(AUDITOR, OPERATOR, ADMIN)` 保护（对齐 `AUDIT_FULL_ACCESS_ROLES`）。

### US-8 密码强度要求（首次登录强制改密、过期提醒、不与历史相同）
- **场景**：账号安全加固（本批 P1 底线 / P2 完整策略）。
- **验收标准**：
  - AC8-1（P1 底线）：管理员创建用户后，首次登录 `must_change_password=1` → 登录成功强制跳改密页；改密后清除标记。
  - AC8-2（P2）：最短长度 ≥8、至少含数字+字母（复杂度策略可配置）。
  - AC8-3（P2）：密码有效期（如 90 天）到期提醒；过期后可配置强制改密。
  - AC8-4（P2）：新密码不能与最近 N（如 3）次历史密码相同（`password_history` 存 bcrypt hash 列表）。
  - AC8-5：改密后**撤销该用户全部 refresh_token**（旧 token 失效，安全兜底）。

### US-9 与现有 RBAC 完全兼容：JWT role claim 解析角色，后端行为不变
- **场景**：登录体系上线不影响已有 RBAC 语义。
- **验收标准**：
  - AC9-1：`get_role(payload)` 从 JWT `role` claim 解析——**逻辑零改动**。
  - AC9-2：`require_role(*roles)` 行为不变：dev 放行、生产 JWT+角色、X-Admin-Token 等效管理员。
  - AC9-3：`verify_jwt_if_prod` / `verify_thread_ownership` / `verify_thread_ownership_if_prod` / `verify_audit_thread_access` 行为不变。
  - AC9-4：登录签发的 token 可通过现有全部鉴权依赖（claims 结构与 `issue_test_token` 一致 + `role`/`name`）。
  - AC9-5：`GET /sessions` 仍按 owner 过滤（threads.owner_id == JWT user_id），不回归 M-5。

### US-10 dev 模式兼容：dev token 不可解析时不要求登录，默认 dispatcher
- **场景**：本地开发保持现有零登录体验。
- **验收标准**：
  - AC10-1：dev 模式（无 APP_ENV=production）**不强制登录**；`verify_jwt_if_prod`/`require_role` 维持 dev 放行。
  - AC10-2：dev token（`gridmind-dev-token`，不可解析）→ 前端 `getJwtRole` 默认 dispatcher、显示「访客/调度员」——现状不变。
  - AC10-3：dev 模式提供「以 X 角色登录」快速按钮（仅 `not settings.is_production` 时后端开放 `/auth/dev-login`），可签发带指定 `role` claim 的真实 JWT 用于前端联调。
  - AC10-4：生产构建/生产环境**绝不暴露** `/auth/dev-login`（404 或门禁拒绝）。

## 四、数据结构草案

> 迁移方式：沿用 `mcp_tools/db/database.py` 的幂等 PRAGMA 模式；三张表均建在主库 `data/gridmind.db`。

### 4.1 `users`

```sql
CREATE TABLE IF NOT EXISTS users (
    id                    TEXT PRIMARY KEY,             -- UUID（登录后写入 JWT sub/user_id）
    username              TEXT NOT NULL UNIQUE,         -- 登录名（小写唯一）
    email                 TEXT,                         -- 可选，UNIQUE（未启用邮箱登录时可为 NULL）
    password_hash         TEXT NOT NULL,                -- bcrypt hash（bcrypt 72 字节截断）
    role                  TEXT NOT NULL DEFAULT 'dispatcher',  -- 5 角色之一（对齐 ROLE_VALUES）
    disabled              INTEGER NOT NULL DEFAULT 0,   -- 1=禁用（登录与 refresh 均拒绝）
    must_change_password  INTEGER NOT NULL DEFAULT 0,   -- 1=首次登录强制改密
    password_changed_at   TEXT,                         -- UTC ISO
    password_history      TEXT NOT NULL DEFAULT '[]',   -- JSON 数组：最近 N 次 bcrypt hash（P2）
    failed_attempts       INTEGER NOT NULL DEFAULT 0,   -- 连续失败计数（登录成功/锁定后清零）
    locked_until          TEXT,                         -- 锁定截止 UTC ISO；NULL=未锁定
    last_login_at         TEXT,                         -- 最近成功登录时间（UTC ISO）
    created_at            TEXT NOT NULL,                -- UTC ISO
    updated_at            TEXT NOT NULL                 -- UTC ISO
);
CREATE INDEX IF NOT EXISTS idx_users_username ON users(username);
CREATE INDEX IF NOT EXISTS idx_users_role ON users(role);
```

### 4.2 `refresh_tokens`（支持多设备并发会话）

```sql
CREATE TABLE IF NOT EXISTS refresh_tokens (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id       TEXT NOT NULL REFERENCES users(id),
    token_hash    TEXT NOT NULL UNIQUE,      -- SHA-256(refresh_token)，不存明文
    expires_at    TEXT NOT NULL,             -- UTC ISO
    created_at    TEXT NOT NULL,
    revoked_at    TEXT,                      -- 退出/轮换/改密后置值
    replaced_by   INTEGER,                   -- 轮换链：新 refresh_tokens.id（NULL=未轮换）
    user_agent    TEXT,
    ip_address    TEXT
);
CREATE INDEX IF NOT EXISTS idx_refresh_user ON refresh_tokens(user_id);
CREATE INDEX IF NOT EXISTS idx_refresh_hash ON refresh_tokens(token_hash);
```

### 4.3 `auth_audit_log`（与 hitl_audit_log 共存）

```sql
CREATE TABLE IF NOT EXISTS auth_audit_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    event_type  TEXT NOT NULL,   -- login_success|login_failed|account_locked|logout|refresh|user_created|user_disabled|role_changed|password_changed
    user_id     TEXT,
    username    TEXT,
    ip_address  TEXT,
    user_agent  TEXT,
    detail      TEXT,            -- 补充（如失败原因类别、目标角色等；不存密码/明文 token）
    created_at  TEXT NOT NULL    -- UTC ISO
);
CREATE INDEX IF NOT EXISTS idx_auth_audit_user ON auth_audit_log(user_id);
CREATE INDEX IF NOT EXISTS idx_auth_audit_time ON auth_audit_log(created_at);
```

### 4.4 种子数据
- 启动迁移时（幂等）创建内置 `admin` 账号（用户名 `admin`、随机初始密码打印一次到日志、`must_change_password=1`）；生产环境**必须**通过 env 注入初始管理员（如 `ADMIN_INITIAL_PASSWORD`）并提示首次改密。

## 五、API 契约

> 约定：统一错误体 `{"detail": "..."}`；鉴权头 `Authorization: Bearer <access_token>`；dev 模式不强制鉴权（`verify_jwt_if_prod` 语义）。

### 5.1 `POST /auth/login`（公开，P0）
请求：
```json
{ "username": "alice", "password": "******" }
```
响应 `200`：
```json
{
  "access_token": "<jwt>",
  "refresh_token": "<opaque>",
  "token_type": "bearer",
  "expires_in": 900,
  "user": { "id": "uuid", "username": "alice", "display_name": "许清楚", "role": "admin" }
}
```
错误：
- `401` 用户名或密码错误（账号不存在/密码错，统一文案，不暴露存在性）
- `403` 账号已被禁用
- `423` 账号已锁定（`Retry-After` 头带剩余秒数）
- `429` IP 限流

### 5.2 `POST /auth/refresh`（公开，P0）
请求：
```json
{ "refresh_token": "<opaque>" }
```
响应 `200`：同 login（新 access_token + **轮换后**的新 refresh_token，旧 refresh 置 `revoked_at`）。
错误：`401` refresh 无效/过期/已撤销/用户被禁用。

### 5.3 `POST /auth/logout`（公开，P0，可选——纯前端清 token 也行）
请求：
```json
{ "refresh_token": "<opaque>" }
```
响应 `200 {"ok": true}`（revoke 对应 refresh 行；幂等——已撤销/不存在也返回 200）。

### 5.4 `GET /auth/me`（Bearer，P0）
响应 `200`：
```json
{
  "id": "uuid", "username": "alice", "display_name": "许清楚",
  "role": "admin", "must_change_password": false, "last_login_at": "2026-08-11T09:00:00+00:00"
}
```
错误：`401` 无效/过期 token。

### 5.5 `GET /users`（管理员，P1）
- 依赖：`require_role(Role.ADMIN)`（dev 放行，见 §九）。
- 响应 `200`：`[{ "id","username","email","role","disabled","must_change_password","last_login_at","created_at" }]`（**不含 password_hash**）。
- 查询参数：`role`/`disabled` 过滤、`q` 关键字（username/email 模糊）、`page`/`page_size`。

### 5.6 `POST /users`（管理员，P1）
请求：`{ "username","email"?,"password","role" }`
响应 `201`：创建的用户（不含 hash）；默认 `must_change_password=1`。
错误：`409` 用户名/邮箱已存在；`422` 角色非法（非 5 角色之一）。

### 5.7 `PATCH /users/{id}`（管理员，P1）
请求（至少一项）：`{ "role"?, "disabled"?, "password"? }`
响应 `200`：更新后用户（不含 hash）。
错误：`404` 用户不存在；`422` 角色非法；`409` 用户名冲突（如支持改名）。

### 5.8 `POST /auth/dev-login`（**仅 dev**，P0 联调用）
请求：`{ "role": "admin" }`（5 角色之一）
响应：同 login（签发带 `role` claim 的真实 JWT）。
约束：`settings.is_production` 时**必须 404**；生产构建前端不渲染入口。

## 七、与 RBAC / 多用户架构的关系

1. **角色来源不变**：登录后仍从 JWT `role` claim 解析（`get_role` 零改动）；`require_role` / `verify_jwt_if_prod` / `verify_thread_ownership` / `verify_audit_thread_access` / `ensure_thread_owned` **行为完全不变**。
2. **决策变更声明**：multiuser PRD Q3「不建用户表」被本 PRD **正式推翻**——真实登录必须有 `users` 表；但这**不影响 RBAC 语义**，只是把「谁有资格拿 role claim」从「token 自证」改为「登录验证后签发」。
3. **owner 一致性**：登录后 JWT `sub`/`user_id` = `users.id`；新会话 `create_thread(owner=users.id)`；`GET /sessions` 按 owner 过滤不变（M-5 不回归）。
4. **存量数据**：dev 历史 thread 的 `owner_id="dev"` 保留；dev 模式不校验 owner（放行），生产模式新用户只看到自己新建的会话（符合预期，无需迁移历史）。
5. **X-Admin-Token 保留**：灰度/管理端口的 admin token 等效管理员逻辑不动（兼容既有运维客户端）。
6. **新增端点鉴权口径**：
   - `/auth/login|refresh|logout`：公开（无鉴权）；
   - `/auth/me`：`Depends(verify_jwt_if_prod)`（dev 放行、生产强制 JWT）；
   - `/users*`：`Depends(require_role(Role.ADMIN))`（dev 放行）；
   - 审计读：沿用 `verify_jwt_if_prod` + `AUDIT_FULL_ACCESS_ROLES` 口径。

## 八、安全设计

1. **密码 hash**：`bcrypt`（已装 5.0.0，成本因子 12；注意 bcrypt 72 字节上限，超长先截断）。**必须**将 `bcrypt` 显式加入 `requirements.txt`（当前为传递依赖，易丢失）。不引入 passlib（纯 bcrypt 足够）。
2. **JWT 密钥**：复用 `JWT_SECRET` env（生产门禁已强制覆盖默认值）；`jwt_algorithm=HS256`；`issuer=gridmind`。
3. **Access token TTL**：新增配置 `JWT_ACCESS_TTL_SECONDS`（默认 900s=15min）；**Refresh token TTL**：`JWT_REFRESH_TTL_SECONDS`（默认 604800s=7d）。
4. **Refresh token 安全**：明文仅返回一次（登录/轮换时）；DB 只存 SHA-256 hash；每次刷新**轮换**（旧 token 立即 `revoked_at`，`replaced_by` 成链）；改密/禁用/登出 → 撤销该用户全部或对应 refresh。
5. **登录限流**：双层——per-account `failed_attempts`（5 次锁定 15min）+ per-IP slowapi（`/auth/login` 10 次/min/IP）。
6. **防枚举**：登录失败统一「用户名或密码错误」；锁定/禁用文案不解释原因；响应时间尽力恒定（伪造用户时也执行一次 bcrypt 比对，避免时序侧信道）。
7. **HTTPS 强制（生产）**：`APP_ENV=production` 时由部署侧（nginx/网关）强制 TLS；后端可加中间件：非 `https`/代理头缺失时拒绝（P1 可选项）。
8. **Token 存储 XSS 权衡**：用户要求存 localStorage，但既有架构明确「不存 localStorage（防 XSS，红色风险）」。默认折中方案：**access_token 存内存（Pinia）** + **refresh_token 存 localStorage**（refresh 仅用于换 access，泄露面小但仍需 XSS 防护）；若坚持全存 localStorage，需在 PRD 评审明确接受风险。→ §十 待确认。
9. **改密安全**：改密需当前密码验证；新密码强度校验（P2）；改密后撤销全部 refresh。
10. **审计不阻断**：审计写库失败仅告警，不阻塞登录主流程。

## 九、dev 模式兼容

1. **默认 dev 体验不变**：`APP_ENV` 未设 → `verify_jwt_if_prod`/`require_role` 全部放行；`gridmind-dev-token` 不可解析 → 前端默认「访客/调度员」——现状零改动。

## 十、待确认问题（主理人拍板）

1. **SSO**：是否有现成 OIDC/SAML？若有，登录页是否加「企业 SSO」入口（P2 预留 vs 本批接入）。

9. **角色变更生效时机**：现有 token 保留到过期（默认），还是要求即时踢下线（强制重新登录）？
